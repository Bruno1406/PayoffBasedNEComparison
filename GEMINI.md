# Project Rules & Assistant Guidelines

## 1. Spec-Driven Implementation Workflow (Mandatory)
Whenever the user requests to implement something according to a specification (e.g., in `specs/` or referenced directly):
- **Do NOT proceed immediately to implementation.**
- First, rigorously review and **criticize the spec**, actively identifying weaknesses, ambiguities, or theoretical gaps.
- Ask clarifying questions across four dimensions:
  1. **Mathematics & Algorithms**: Formulations, convergence proofs/assumptions, edge cases, numerical conditioning, and coordinate invariance.
  2. **Features & Interfaces**: Method signatures, class hierarchy, data structures, and compatibility with existing components (`Game`, etc.).
  3. **Testing & Validation**: Acceptance criteria, ground truth benchmarks, synthetic test games, and tolerance thresholds.
  4. **Performance & Potential Pitfalls**: Bottlenecks, vectorized linear algebra, high rejection rates, and memory scaling.
- Wait for user alignment or answers before writing implementation code.

## 2. Code Style & Standards
- **Consistency**: Maintain exact architectural and stylistic consistency with existing Python modules in `payoffnash/` (`common.py`, `zo_gradient_play.py`, `ne_seeking.py`).
- **Typing**: Use modern Python 3.10+ type annotations throughout (`list[...]`, `tuple[...]`, `Optional[...]`, `Callable[...]`, `np.ndarray`).
- **Minimal Comments**: Keep comments minimal. Code should be clean, idiomatic, and self-documenting. Use brief comments only when referencing specific equations from papers or clarifying non-obvious mathematical derivations. Avoid redundant explanations of self-evident code.
- **Vectorization**: Prefer vectorized NumPy operations (`np.ndarray`, `np.linalg`, broadcasting) over explicit Python loops for mathematical computation.
- **Modular Imports**: Maintain the dual-execution fallback pattern to allow both package imports and direct script execution:
  ```python
  try:
      from .common import Game
  except (ImportError, ValueError):
      try:
          from payoffnash.common import Game
      except ImportError:
          from common import Game
  ```
- **Naming Conventions**:
  - Modules: `snake_case.py`
  - Classes: `PascalCase`
  - Functions & Variables: `snake_case`

## 3. Workspace Hygiene & Notebook Architecture
- **Root Code Must Be Jupyter Notebooks**: Every piece of code that is not part of the package `payoffnash`, not a unit/integration test in `tests/`, and that lives at the root of the repository (e.g., analyses, experiments, debugging, investigations, benchmark runners) **must be a self-contained Jupyter notebook (`.ipynb`)**. No loose or auxiliary `.py` runner/scratch scripts are permitted at the root of the repository.
- **Delete Ephemeral Build Scripts**: Ephemeral build and notebook generator scripts (e.g., `build_*_notebook.py`, temporary runner scripts) must be deleted once their target notebooks/artifacts have been generated. Do not retain temporary builder scripts in the repository.
- **User-Controlled Notebook Execution**: The assistant should build, structure, and populate the notebooks (`.ipynb`) with clean code, formulas, and markdown, but **the user is responsible for running them**. The user maintains control over the execution flow and resource allocation, so the assistant should not unilaterally launch heavy notebook runs or long-running simulation jobs in the background.

## 4. Experiment Data & Artifact Organization
- **Dedicated Data Subfolders**: All data generated by an experiment, benchmark, or investigation execution must reside in a dedicated subfolder within `data/`.
- **Subfolder Naming Pattern**: Each subfolder must strictly follow the pattern:
  `data/{id}_{short_representative_name}/` (e.g., `data/01_cournot_investigation/`, `data/02_mtbo_100_games/`).
- **Co-located Artifacts**: The designated subfolder must contain all relevant outputs generated by that run, including CSV files, metrics tables, and image files (`.png`, `.jpg`). No raw data files or plots should be written directly to the root of the repository or generic root folders.

## 5. Project Scope, Retrocompatibility & Test Adaptation
- **No Backward Compatibility Burden**: This codebase is developed exclusively for a single-user bachelor thesis project. Do NOT worry about retrocompatibility or retaining deprecated legacy parameters (`num_iters`, `N_iters`, legacy aliases, etc.). Keeping legacy parameters and compatibility shims only clutters the code.
- **Tests Adapt to Code Changes**: Whenever a function signature, interface, or output data structure is modified or modernized, the tests in `tests/` must adapt to the new code, never the other way around.
